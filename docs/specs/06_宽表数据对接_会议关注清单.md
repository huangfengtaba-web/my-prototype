# 宽表数据对接 · 明日会议关注清单（项目经理视角）

> 背景：业务侧要求开发**完全基于 MES 表的生产数据形成宽表**，替代/收拢现有 SOURCE_* 12+ 张分散源表。
> 时间锚点：计划 sheet「宽表数据同步完成 = 10/28（海辉）」；「同步字段确认 序号24 剩余字段开发 10/28」；原型评审 10/31（黄鹏）。
> 立场：宽表是**数据供给方式的重构**，不是简单的"加一张表"——它改变的是同步机制、字段责任边界和数据质量责任。本清单按"必须今天拿到结论"的优先级排列。

## A. 范围与字段级确认（最高优先级，直接决定 10/28 能否达成）

1. **字段清单逐字段过一遍并冻结版本**：宽表 1 张 ≠ 责任 1 家。必须产出《宽表字段确认表》：字段名 / 来源 MES 表.字段 / 转换规则 / FSO 消费方 / 数据 Owner（MES 侧接口人）五列，双方签字。已有基础：序号24 已确认 11 张 SOURCE_* 表的映射（MAP-LOT / MAP-RTS 版本），剩余字段 10/28 开发——**明日必须拿到"剩余字段 diff 清单"而不是口头"快好了"**。
2. **C 级缺口表是否进宽表**：Litho OverLap（12 列表头空白）与 Wafer 加工时间（整表空白）两张客户源表——若纳入宽表，这是最后一次低成本补齐的机会；若不纳入，明确"阶段二补"并落在会议纪要。
3. **Reticle 状态数据源问题（易漏的高风险项）**：宽表出自 MES，但 Reticle 实时位置 / IRIS 计时计片 / Pod 状态来自 **EAP 事件流与 SDR 回执**，MES 里没有或延迟极大。要明确：宽表是否覆盖 Reticle 域？若不覆盖，FSO 保留 EAP/SDR 第二通道（data_zone 已按双通道设计），避免"宽表单通道"假设导致光罩推演无米下锅。
4. **Flag 类字段口径**：PiRun / Monitor / KeyLot / MoveTarget / Ship Lot / MES Queue 插队 / Module Quota / OverQTime——这些决定排程优先级的标志位，MES 侧是否有现成字段？没有的话谁负责维护宽表中的该列？（多数是阶段二需求 26–30，但字段要**现在留列**，否则日后改宽表结构要重新走冻结流程。）
5. **QTime 给配置还是给剩余量**：宽表若只给 QTIME_LIMIT 配置，remainQt 由 FSO 计算（现状）；若 MES 直接给 REMAIN_QTIME，要确认其计算口径（含不含当前站 PT、rework 特例——设计书 §4.2.2 的 Case 1/2/3 必须与 MES 口径对齐，否则两侧数字对不上）。
6. **LOTHIST 是否随宽表**：BARC 24 小时来货预排、Coming WIP、Stacking Bond 未来负载推演都依赖交易历史。确认宽表是否携带 LOTHIST 或保留独立通道 + 回补 N 天历史。

## B. 机制口径（决定联调会不会返工）

7. **增量水位与延迟 SLA**：宽表的增量方式（时间戳 / CDC / 全量刷）与**数据延迟 SLA**（建议 ≤5 分钟，急货场景 10 分钟重排节奏下，延迟 >10 分钟等于排程基于过期数据）。写进纪要：水位字段名、断点续传约定、失败重试策略（FSO 侧已有 3 次退避 1/5/15min）。
8. **时间 / 时区 / 单位**：统一 yyyy-MM-dd HH24:mi:ss、东八区、PT 单位（分钟还是秒）——历史教训类问题，逐项 30 秒确认，避免联调第一天全在改格式。
9. **宽表是否允许 FSO 回写**：FSO 会往 SOURCE_RETICLE_STATUS 回写 EARLIEST_AVAILABLE_TIME/LOCATION（推演起点）。宽表若是 MES 单向生产的只读物，这两字段必须移出宽表或允许 FSO 侧扩展列——**读写边界不明是宽表项目最典型的返工点**。
10. **主数据变更生效机制**：Product Flow / Recipe 变更在宽表中如何体现版本（FSO_FIELD_MAPPING 已按"改版本不即时生效、随全量刷新切换"设计）——确认 MES 侧变更通知方式与冻结期约定（宽表结构变更需提前 N 天通知）。
11. **历史回补**：上线基线需要回补多少天（建议 ≥30 天：Stacking 推演要 30 天、计划 vs 实际校准要有样本、Run Trace 重放要有历史）。

## C. 数据质量与责任（决定"数据不对"时吵架找谁）

12. **对账口径与阈值签认**：FSO data_zone 已有 4 项对账（WIP 当站 / 在库 Reticle / QTime 行数 / Eqp 状态）。明日确认：对账以**宽表为准还是 MES 原表为准**（建议宽表，因为它才是消费对象）、差异阈值（建议当站 WIP ≤2）、超阈值处置流程。
13. **隔离区处置 SLA**：脏数据（ENUM 非法 / Flow 缺失 / 互斥标识冲突）进隔离区后，**谁在多长时间内修复**（建议 MES 侧 4 小时 SLA，超时升级 DATA_ERROR 且该表冻结参与排程）。

## 一页纸结论（可投屏）
- **今天必须带走的三样东西**：①字段级确认表（含 diff）②Reticle/LOTHIST 是否走宽表的结论 ③对账阈值与隔离 SLA 签认。
